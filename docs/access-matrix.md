# Матриця доступу ЛР04 — baseline 2-A, рівень «Добре»

Достатній = «Задовільно», добрий = «Добре», відмінний = «Відмінно»; рівні накопичувальні.
Виконується рівень **добрий**. Allow — право на конкретну дію над конкретним ресурсом, а не лише успішний login.

Предметне правило baseline 2-A: Reporter створює й редагує власний запис; Analyst читає інциденти для аналізу
і може перевести лише `New → Triaged`; Administrator має тільки прямо опубліковані права. Для поточного
потоку таких прав немає, тому для Administrator скрізь deny.

## Політика HTTP-відмов

| Ситуація | Відповідь |
|---|---|
| Немає автентифікації | `401` без HTML redirect |
| Автентифікований користувач **не має права читати** ресурс (чужий інцидент, чужий коментар, internal comment для Reporter, будь-який інцидент для Administrator) | `404`, **такий самий**, як для неіснуючого id: той самий `title`, без `detail` з id |
| Користувач **може читати** ресурс, але операція йому не дозволена (Analyst робить update/delete; Reporter робить triage власного інциденту) | `403` |
| Операція дозволена, але поточний стан її не допускає | `409` |
| Невалідне тіло запиту | `400` |

**Обґрунтування 404.** UUID інцидентів і коментарів не є секретом: вони потрапляють у посилання, журнали,
знімки екрана. Якщо для чужого id сервер відповідає інакше, ніж для неіснуючого, Reporter може з'ясувати,
які інциденти існують, хоча прочитати їх не може. Тому для того, хто не має права читати ресурс, чужий і
неіснуючий id нерозрізнювані (перевіряє A-10). `403` лишається там, де користувач і так бачить ресурс
(Analyst, власник), тож відмова нічого нового не розкриває.

Порядок рішення в кожному маршруті одного інциденту: 401 → чи може читати (інакше 404) → чи дозволена
операція (інакше 403) → чи допускає стан (інакше 409) → зміна.

## Додаткові правила

- **Child resource**, через який можна непрямо отримати дані головного ресурсу: `IncidentComment`
  (`GET /api/incident-comments/{id}`). Сам коментар не має власника для авторизації; право читати його
  випливає з права читати батьківський інцидент, а internal comment додатково вимагає роль Analyst.
  Те саме правило діє в details-проєкції.
- **Update DTO** містить лише `title` і `description`. `ownerUserId`, `status`, `severity`, `role` та інші
  поля сервер ігнорує (A-08a). Severity і status змінюються лише окремими операціями.
- **Triage**: сервер сам читає поточний статус і сам встановлює `Triaged`; статус із тіла запиту не
  приймається. Тіла запит не потребує.
- **Audit**: кожна відмова в triage (403 або 404) записує подію `authorization.denied` з полями subject id,
  action, resource id, result, UTC-час і traceId, що збігається з traceId у тілі відповіді. Пароль, cookie,
  token і тіло запиту в подію не потрапляють.
- **Роль** береться лише з перевіреного principal (cookie), ніколи з тіла запиту. Після зміни ролі
  потрібен повторний login.
- **CSRF** для cookie-автентифікованих mutation (PUT, DELETE, POST triage) не усувається цією роботою;
  це задокументований навчальний борг до ЛР 6.
